# ADR 0001: 開発は issue と PR で進め、着手とマージは人間が決める

- 日付: YYYY-MM-DD
- 状態: 採用

## 状況
Claude Code に実装を任せつつ、何を任せるかと何を取り込むかは人間が管理したい。

## 決定
- `/plan-issues` が PHASES のタスクを issue にする。実装を任せてよい issue には、人間が `ai-ready` を付ける。
- `/next-task` は `ai-ready` で依存が解決済みの、最小番号の issue を 1 つ実装して PR を出し、止まる。マージは人間が行う。
- ブランチ名は `feat/<issue番号>-<短い英語スラッグ>`。実装以外は `chore/<スラッグ>`。open の PR があるかどうかもブランチ名で判定する。
- 依存関係は issue 本文の「依存する issue」に `- #番号` で書く。
- CI は `check` という 1 ジョブに、型チェック・lint・テストのステップを並べる。実行するコマンドは CLAUDE.md の「検証コマンド」に書く。Actions はコミット SHA で固定する。
- main の保護は `scripts/protect-main.sh` で設定する。承認数は 0 にする。

## 理由
- `ai-ready` と手動マージで、人間の確認点を 2 か所に絞れる。
- 1 ジョブなら依存のインストールが 1 回で済み、Actions の無料枠を節約できる。必須チェックの指定も 1 つで済む。
- 1 人の開発では自分の PR を承認できないので、承認数を 1 以上にすると進めなくなる。

## 却下した案
- 型チェック・lint・テストを別ジョブにする: 失敗箇所は見やすいが、インストールが 3 回になる。
- ラベルなしで `/next-task` が全 issue を対象にする: 人間が内容を確認する前に実装が始まる。
- GitHub Projects や sub-issue で依存を管理する: 1 人の開発には過剰で、コマンドからも読みにくい。

## 結果・影響
- CI のジョブ名 `check` を変えるときは、ブランチ保護の設定（`scripts/protect-main.sh`）も直す。
- 別ジョブの案と比べて、先のステップが失敗すると後のステップの結果が出ない。ローカルでは `/next-task` が 3 つとも実行する。
- Actions の更新は手動で行う。
